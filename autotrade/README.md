# autotrade — 증권사 API 연동 자동매매 프레임워크

> **결론 먼저**: 메리츠증권은 2026년 9월 현재 **개인 개발자용 공개 오픈 API가 확인되지 않는다.**
> 그래서 이 저장소는 (1) 증권사에 종속되지 않는 매매 엔진, (2) 지금 바로 검증 가능한
> 오프라인 시뮬레이터, (3) 한국투자증권(KIS) 실동작 어댑터, (4) 메리츠 API가 나오면
> **JSON 한 장만 채우면 붙는** 어댑터를 함께 담았다.
> 자세한 근거와 대안은 [docs/brokers.md](docs/brokers.md) 참고.

```
전략(Strategy) → 수량/가격 확정(Engine) → 리스크 심사(RiskGuard) → 주문(Broker) → 감사로그(Journal)
                                              ↑ 여기서 막히면 주문은 절대 나가지 않는다
```

---

## 1. 지금 당장 돌려볼 수 있는 것

```bash
cd autotrade
python3 -m pip install -r requirements.txt

python3 -m autotrade.cli doctor        # 환경·설정·안전장치 점검
python3 -m autotrade.cli backtest      # 샘플 데이터로 전략 검증
python3 -m autotrade.cli simulate      # 엔진 전체(주문·체결·리스크) 리허설
python3 -m pytest                      # 125개 테스트
```

`doctor` → `backtest` → `simulate` 까지는 **증권사 계좌도, 네트워크도 필요 없다.**
이 세 개가 깨끗하게 통과하는 상태가 "제반 환경이 갖춰졌다"의 기준선이다.

## 2. 메리츠증권 연동 검토

### 2.1 현재 상황

| 항목 | 상태 |
|---|---|
| 메리츠증권 개인용 공개 REST API | **확인되지 않음** (개발자센터·공개 문서 없음) |
| 업계 보도 | 2026-05 기준 "오픈 API 개발을 사실상 마무리, 내부 테스트 중, 연내 출시 예상" |
| 결합 예상 상품 | 무수수료 `Super365` 계좌 — 자동매매에서 수수료는 성과에 직결되므로 매력적 |

즉 **기다릴 가치는 있지만, 오늘 코드로 붙일 수는 없다.** 최신 상태는 반드시
메리츠증권 고객센터(1588-3400)나 지점에 직접 확인할 것. 이 문서의 조사 시점은 2026-09이다.

### 2.2 그래서 택한 전략 — "증권사는 나중에 갈아끼운다"

전략·리스크·주문관리·감사로그는 증권사와 무관하다. 실제로 증권사마다 다른 건
엔드포인트 주소와 필드 이름뿐이다. 그래서 브로커를 **인터페이스 뒤로 숨기고**,
스펙 JSON으로 갈아끼울 수 있게 만들었다.

```
autotrade/brokers/
  base.py        Broker 인터페이스 (엔진이 아는 유일한 계약)
  paper.py       오프라인 시뮬레이터        ← 지금 바로 사용 가능
  kis.py         한국투자증권 REST 구현     ← 지금 바로 사용 가능
  spec_rest.py   스펙(JSON) 기반 범용 어댑터
  meritz.py      메리츠 — spec_rest 위에 얹은 껍데기 ← API 출시되면 즉시 사용
```

메리츠 API가 공개되면 할 일은 이것뿐이다.

```bash
cp config/meritz.spec.example.json config/meritz.spec.json
# 공식 문서를 보고 TODO_ 로 시작하는 값(엔드포인트 경로·필드명·주문코드)을 채운다
AUTOTRADE_MODE=meritz python3 -m autotrade.cli doctor
```

TODO가 하나라도 남아 있으면 어댑터가 **기동을 거부한다**. 반쯤 채운 설정으로
실계좌에 주문이 나가는 사고를 원천 차단하기 위해서다.

### 2.3 그때까지의 현실적인 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 메리츠 API 출시를 기다리며 시뮬레이터로 개발** | 계좌 개설 불필요, 리스크 0 | 실전 체결 특성을 못 배운다 |
| **B. 한국투자증권 계좌를 자동매매 전용으로 추가 개설** (권장) | 오늘 바로 실전 검증 가능, 모의투자 서버 제공 | 계좌가 하나 늘어난다 |
| **C. 메리츠 HTS/MTS 화면을 매크로로 자동화** | — | **하지 말 것** (아래) |

> ### ❌ C안을 배제하는 이유
> 공식 API가 없다고 화면 매크로나 내부 통신 리버스 엔지니어링으로 우회하는 접근은
> - 대부분의 증권사 전자금융거래 약관에서 **금지행위**로 규정한다 → 계좌 이용 제한·거래 정지 사유
> - 화면·내부 규격이 예고 없이 바뀌면 **주문이 조용히 실패하거나 잘못 나간다**
> - 사고가 나도 증권사 보상이나 분쟁조정을 기대하기 어렵다
>
> 자동매매에서 가장 비싼 버그는 "돈이 걸린 채로 조용히 틀리는 것"이다. 이 경로는 그 위험이 구조적이다.

## 3. 필요한 것들 (체크리스트)

### 3.1 계정·서류
- [ ] 증권 계좌 (자동매매 전용 계좌를 따로 두는 것을 강력 권장 — 사고 시 손실 범위가 격리된다)
- [ ] 증권사 개발자센터 가입 및 **앱키/시크릿 발급**
- [ ] **모의투자 계좌** (실계좌 전 검증용. KIS는 별도 서버·별도 앱키를 제공한다)
- [ ] 공동인증서/OTP 등 증권사가 요구하는 인증 수단

### 3.2 기술 환경
- [ ] Python 3.10+ (이 저장소는 3.11에서 검증)
- [ ] 상시 구동 환경 — 개인 PC는 절전·재부팅·네트워크 끊김으로 **장중에 죽는다.** 클라우드 VM 권장
- [ ] 시각 동기화(NTP) — 장 시작/마감 판정이 어긋나면 엉뚱한 시간에 주문한다
- [ ] 로그 보관 위치 (감사 로그는 사고 원인 규명의 유일한 근거다)
- [ ] 알림 채널 (텔레그램/슬랙 등) — 주문·에러·킬스위치 발동 시 즉시 알아야 한다

### 3.3 지식·데이터
- [ ] 검증용 과거 시세 (수정주가 반영본. 미반영이면 배당락·액면분할이 가짜 신호를 만든다)
- [ ] **본인 계좌의 실제 수수료율·세율** (`.env`의 예시값을 그대로 쓰면 백테스트가 거짓말을 한다)
- [ ] KRX 호가단위·휴장일 (둘 다 코드에 들어 있지만 **개정되므로 연 1회 갱신 필요**)

## 4. 주의점

### 4.1 법·제도

| 항목 | 내용 |
|---|---|
| **개인의 알고리즘 매매 자체** | 본인 계좌로 본인 자산을 매매하는 것은 합법이다. |
| **남의 돈을 굴리면 불법** | 타인 자금을 모아 운용하거나 수수료를 받으면 자본시장법상 **무인가 투자일임·집합투자**가 된다. 가족·지인 돈도 예외가 아니다. |
| **매매 신호 판매도 규제 대상** | 대가를 받고 종목·매매시점을 제공하면 **유사투자자문업 신고** 또는 투자자문업 인가 문제가 생긴다. |
| **시세조종 금지** | 허수주문(체결 의사 없는 대량 호가 후 취소), 자전거래, 시가·종가 관여 등은 자본시장법 위반이다. **고빈도 주문·취소 반복 로직은 의도가 없어도 시장감시에 걸릴 수 있다.** |
| **프로그램매매 신고** | 일정 규모 이상의 알고리즘 거래는 사전 신고 대상이 될 수 있다. 규모를 키우기 전에 증권사에 확인할 것. |
| **시세 데이터 재배포 금지** | API로 받은 시세를 외부에 공개·판매·재배포하면 계약 위반이다. **공개 저장소에 커밋하지 말 것** (이 저장소는 `.gitignore`로 막아 두었다). |
| **세금** | 국내주식 매매차익은 현재 대주주 외 비과세지만 **증권거래세는 매도마다 부과**된다. 회전율이 높은 전략은 세금·수수료만으로 무너진다. 해외주식·파생은 양도세 신고 의무가 있다. |

> 위 내용은 일반적인 안내이며 법률 자문이 아니다. 운용 규모를 키우거나 타인이 관여하는 순간
> 반드시 전문가에게 확인할 것.

### 4.2 계좌·보안

- **앱키/시크릿은 계좌 주문 권한 그 자체다.** 코드·깃·채팅·스크린샷에 절대 남기지 않는다.
  이 저장소는 `.env`를 `.gitignore`로 막고, 로그에서 키·계좌번호를 자동 마스킹한다.
- `chmod 600 .env`, 토큰 캐시도 `0600`으로 저장한다(구현되어 있음).
- 서버에 두는 경우 SSH 키 인증·방화벽·자동 보안 업데이트는 기본이다.
- **접근토큰은 발급 횟수 제한이 있다.** 재시작마다 새로 받으면 차단된다 → 파일 캐시 재사용(구현되어 있음).
- 유출 의심 시: 증권사에서 **앱키 즉시 폐기 → 재발급**. 이 순서를 미리 익혀 둘 것.

### 4.3 기술적 함정 (실제로 돈이 새는 지점)

| 함정 | 이 저장소의 대응 |
|---|---|
| 호가단위 안 맞아 주문 거부 | `pricing.py` — KRX 틱 테이블, 체결 우선/가격 우선 선택 |
| 미체결 주문이 쌓여 상태가 어긋남 | 기본값을 **체결 우선(marketable) 지정가**로 |
| 같은 신호로 주문 폭주 | 재발주 쿨다운 + 분당/일일 주문 수 상한 |
| 휴장일·장외 시간 주문 | `clock.py` 거래시간·휴장일 판정 |
| 전략 버그로 전 재산 매수 | 1주문/종목당/전체 금액 상한, 화이트리스트 |
| 손실 폭주 | 일중 손실 한도 → **킬 스위치 자동 발동** |
| 네트워크·API 오류로 프로세스 사망 | 루프가 예외를 삼키고 로그 남긴 뒤 계속 |
| 백테스트만 좋고 실전은 손실 | 수수료·세금·슬리피지 반영 + **매수후보유 벤치마크 동시 출력** |
| 사고 후 원인 불명 | 모든 판단·주문을 append-only JSONL 감사 로그로 |

### 4.4 리스크·운영

- **백테스트 수익률은 미래를 보장하지 않는다.** 파라미터를 과거에 맞춰 고르는 순간(과최적화)
  그 숫자는 무의미해진다. 그래서 `backtest`는 항상 매수후보유 수익률을 함께 찍는다.
  **벤치마크를 못 이기면 자동화할 이유가 없다.**
- 시뮬레이터는 호가 잔량·부분체결·거부를 모사하지 않는다. **실전 성과는 시뮬레이션보다 나쁘다.**
- 잃어도 생활에 지장 없는 금액으로 시작한다. 한도는 "이 정도면 되겠지"가 아니라
  **"오늘 이만큼 잃어도 내일 출근할 수 있는가"**로 정한다.
- 자동매매의 최대 리스크는 전략이 아니라 **사람이 손으로 개입하는 것**이다.
  개입할 거라면 킬 스위치로 멈추고 개입한다.

## 5. 구축 로드맵

각 단계를 통과하지 못하면 **다음 단계로 넘어가지 않는다.** 이 순서를 건너뛰는 것이 사고의 주원인이다.

| 단계 | 내용 | 통과 기준 |
|---|---|---|
| **0. 환경** | `pip install -r requirements.txt`, `make doctor` | 오류 0건 |
| **1. 전략 정의** | 진입·청산·손절 규칙을 **말로** 먼저 쓴다 | 애매한 표현이 없음 |
| **2. 백테스트** | `cli backtest` — 수수료·세금 반영 | 매수후보유 대비 우위 + MDD 감내 가능 |
| **3. 엔진 리허설** | `cli simulate` — 리스크 계층 포함 전 구간 | 의도한 주문만 나가고 나머지는 차단됨 |
| **4. 모의투자** | `AUTOTRADE_MODE=kis-paper`, `DRY_RUN=true` | 실제 API 호출 성공, 주문 직전까지 정상 |
| **5. 모의 실주문** | `DRY_RUN=false` (모의 서버) | **최소 2~4주.** 체결·잔고가 로그와 일치 |
| **6. 실계좌 최소금액** | 한도를 아프지 않은 수준으로 | 최소 1개월. 예상과 실제 체결가 차이 확인 |
| **7. 점진적 증액** | 한 번에 두 배 이상 늘리지 않는다 | 매주 감사 로그 리뷰 |

운영 중 매일 확인할 것은 [docs/operations.md](docs/operations.md)에 정리했다.

## 6. 구조

```
autotrade/
├─ autotrade/
│  ├─ config.py        환경변수 설정 + 실계좌 안전장치
│  ├─ models.py        Order/Position/Candle/Signal 등 도메인 모델
│  ├─ clock.py         KRX 거래시간·휴장일
│  ├─ pricing.py       호가단위(틱) 보정, 수량 산출
│  ├─ risk.py          ★ 리스크 계층 — 모든 주문이 통과하는 관문
│  ├─ engine.py        ★ 매매 엔진 — 주문이 나가는 유일한 경로
│  ├─ backtest.py      비용 반영 백테스트 + 벤치마크
│  ├─ journal.py       감사 로그(JSONL) + 비밀값 마스킹
│  ├─ cli.py           명령줄 진입점
│  ├─ brokers/         base / paper / kis / spec_rest / meritz
│  └─ strategies/      base / sma_cross / buy_and_hold
├─ config/             브로커 스펙 JSON (메리츠 템플릿)
├─ data/               휴장일, 샘플 합성 데이터
├─ tests/              125개 테스트
└─ var/                감사 로그·토큰 캐시·킬 스위치 (git 제외)
```

**설계 원칙**

1. 기본값은 항상 안전한 쪽 — `mode=paper`, `dry_run=true`, 화이트리스트 비어 있으면 **전부 차단**
2. 주문 경로는 하나뿐 — 엔진 밖에서 주문하는 코드는 존재하지 않는다
3. 전략은 "의도"만, 발주 여부는 리스크 계층이 결정
4. 모든 판단을 append-only 로그로 남긴다

|---|---|
| `doctor` | 설정·의존성·달력·권한·안전장치·연결 점검 |
| `backtest --csv ... --trades` | 과거/샘플 데이터 백테스트 |
| `simulate --cycles 200` | 오프라인 엔진 리허설 |
| `quote --symbol 005930` | 현재가 조회 (연결 확인) |
| `balance` | 잔고 조회 |
| `fetch --symbol 005930 --out data/005930.csv` | 일봉 CSV 저장 |
| `run --symbols 005930` | 운영 루프 (**기본 드라이런**) |
| `run --live-orders` | 실제 주문 전송 (실계좌면 `START` 입력 요구) |
| `kill` / `unkill` | 킬 스위치 ON/OFF |

전략 옵션: `--strategy sma_cross --fast 5 --slow 20 --notional 200000`

## 8. 안전장치 요약

| 장치 | 동작 |
|---|---|
| 드라이런 | 기본 ON. 주문 직전까지 가고 전송하지 않음 |
| 실계좌 이중 잠금 | `AUTOTRADE_I_UNDERSTAND_REAL_MONEY_RISK` + 화이트리스트 필수 + `START` 입력 |
| 종목 화이트리스트 | 비어 있으면 **모든 주문 차단** (기본값) |
| 금액 한도 | 1주문 / 종목당 / 전체 익스포저 3단 |
| 일중 손실 한도 | 초과 시 킬 스위치 자동 ON, 당일 전면 중단 |
| 주문 빈도 제한 | 분당·일일 상한 + 동일 신호 쿨다운 |
| 공매도 차단 | 보유 수량 초과 매도 불가 |
| 거래시간 검사 | 정규장 외 주문 차단 |
| 수동 킬 스위치 | 파일 하나로 즉시 전면 중단 (`make kill`) |
| 감사 로그 | 모든 판단·차단·주문을 JSONL로 |
| 비밀값 마스킹 | 로그에서 앱키·시크릿·계좌번호 자동 제거 |

## 9. 한계 (반드시 읽을 것)

- 이 저장소는 **뼈대와 안전장치**다. **수익을 내는 전략은 들어 있지 않다.**
  포함된 `sma_cross`는 배관 검증용이며, 샘플 데이터에서 매수후보유에 진다.
- 시뮬레이터는 호가 잔량·부분체결·거부·시장충격을 모사하지 않는다.
- KIS의 TR_ID·엔드포인트는 개정될 수 있어 **운영 전 최신 문서 대조가 필요**하다(환경변수로 덮어쓸 수 있게 해 두었다).
- `data/krx_holidays.txt`는 초안이다. **KRX 공식 공지로 검증·갱신해야 한다.**
- 투자 손익은 전적으로 이용자 본인의 책임이다.
